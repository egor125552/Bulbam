# E2EE v2: реально передаваемые зашифрованные конверты устройств

## Что реализовано

Запущенный Cloudflare Worker с D1 принимает только структурированный шифротекст на `POST /api/v1/chats/{id}/e2ee/envelopes`. Клиент генерирует одноразовый отправительский ECDH P-256 ключ **для каждого получателя каждого сообщения**, выводит AES-256-GCM ключ через HKDF-SHA-256 с привязкой к разговору, отправителю, обоим устройствам, ID сообщения и открытому ключу отправки, шифрует сообщение на устройстве и подписывает конверт ECDSA ключом зарегистрированного устройства. Приватные ключи не отправляются на сервер.

Сервер проверяет принадлежность отправителя к диалогу, доверие отправляющего и принимающего устройств, подпись, соответствие recipientUserId участникам и предел размера. Открытый текст не принимается в этом API ни как поле, ни как допустимый тип payload. Конверты хранятся для каждого устройства отдельно; повтор по прежнему clientMessageId идемпотентен только при **идентичном** шифротексте.

Получатель запрашивает свою очередь, проверяет подпись и AES-GCM, сохраняет **шифротекст** вместе с проверенным ключом отправителя в локальный IndexedDB и лишь затем отправляет подписанное ECDSA подтверждение доставки. Чужой аккаунт и неподписанный ACK не могут очистить очередь. Даже после отзыва ключа отправителя получатель сохраняет подписанный снимок identity на момент отправки, чтобы открыть доставленный ранее конверт. Собственным другим доверенным устройствам отправителя направляются отдельные шифрованные копии. В существующем списке сообщений подключено чтение локальной зашифрованной истории и новых конвертов.

Сервер отправляет только событие `e2ee.envelope.created` с метаданными и push «Новое сообщение», **без текста сообщения**. Отправка и получение без дополнительного Worker, поверх того же Cloudflare Worker/D1. При локальном тестировании используются настоящие endpoint'ы работающего Worker, D1 и два реальных сеанса тестовых аккаунтов. Тесты проверяют отсутствие открытого текста в D1, расшифровку, повторную локальную историю, отклонение постороннего аккаунта, изменение шифротекста, неподписанное подтверждение и неизменность idempotency-ключа.

## Важная граница готовности

**Это не Double Ratchet, не PQXDH и пока не полная замена действующей обычной переписки.** Получательский ECDH identity ключ долговременный: его компрометация потенциально позволяет расшифровать ранее перехваченные v2 конверты. Одноразовый ключ отправителя не обеспечивает прямой секретности получателя. Для новых личных голосовых без старого ключа используется формат зашифрованных аудиочастей `encrypted-voice;v=1` с **отдельным случайным AES-256-GCM ключом каждой записи**, но общий секрет записи доставляется только внутри подписанных E2EE v2 конвертов каждому доверенному устройству собеседника и собственным устройствам отправителя. Сервер сохраняет аудио только в зашифрованном виде, не получает ключ. Существующие защищённые записи со старым общим ключом остаются совместимыми; это миграционный режим, не Signal. Голосовые в группах пока не переведены на новую модель. В экспериментальной ветке обычная кнопка личного чата и запись голосовых теперь выбирают v2 конверты при включённой функции защиты, даже если сохранён старый общий ключ. При сбое проверки защиты отправка не переходит в открытый текст. Сообщения из старой истории по-прежнему читаются своим прежним способом. Ветка не опубликована на рабочем сайте и не должна заявляться как Signal или прошедшая аудит.

Нужно заменить самодельный v2 обмен реализацией проверенного PQXDH/Double Ratchet, подключить атомарные one-time prekeys, динамическое доверие, изоляцию сессий по устройствам, устойчивую multi-device delivery/retry, дальнейшее усиление E2EE медиа, безопасную миграцию и тесты Safari/VoiceOver на устройствах. Официальный `libsignal` пока не предоставляет поддерживаемый браузерный WebAssembly API; независимая OpenE2EE TypeScript реализация существует, но не имеет независимого криптографического аудита. Не рекламировать текущую реализацию как Signal или как полную многодевайсную защиту.

### Голосовые и устойчивость доставки

В `web/js/voice-recorder.js` запись новых личных голосовых при включённой функции и доступных доверенных устройствах шифруется ещё до передачи WebSocket. Ключ передаётся только после публикации зашифрованного аудиофайла. Получатель импортирует ключ из адресованного ему E2EE-конверта и воспроизводит через существующий декодер AES-GCM, учитывающий целостность всех аудиочастей. Голосовые без ключа не переходят бесшумно в plaintext, а отсутствие подтверждённых устройств останавливает запись до включения микрофона. Черновик удерживается до подтверждения публикации ключевых конвертов. При частичной отправке уже созданные шифротексты хранятся в локальной очереди и повторяются без смены nonce/шифротекста для прежнего `clientMessageId`.

**Ограничения:** новая ветка не заменяет старую систему голосовых в группах. Долговременный ECDH-ключ v2 не даёт Signal-подобную forward secrecy. На настоящем iPhone Safari требуется аппаратная проверка MediaRecorder, VoiceOver, прерываний и работы в фоне.

## Реальная проверка

`npm test -- --run test/e2ee-device-messages-live.test.js` поднимает настоящий Cloudflare Worker, D1 и реальные HTTP обработчики в отдельном локальном тестовом окружении. Не требует production-паролей и не обращается к существующим пользовательским аккаунтам. Проверка на deployed production и на настоящем Safari iPhone после release остаётся отдельно.

### Автоматическая отправка и восстановление

Новая версия личного чата создаёт подписанные конверты для всех доверенных устройств получателя и отправителя и сохраняет зашифрованные пакеты перед первой попыткой доставки. Если вкладка закрылась при отправке, клиент может продолжить сохранённую очередь без исходного текста после следующего открытия переписки. Отказ владельца от защиты не приводит к незаметной открытой пересылке уже зашифрованного черновика. Сохранённые ключи удаляются из оперативной памяти после отмены или удаления черновика голосового.

Все эти возможности проверяются тестами маршрутизации и тестовым сервером. Аппаратные испытания iPhone/VoiceOver и независимый аудит необходимы до выпуска.

### Отображение в списке чатов

После сохранения первого нового зашифрованного конверта сервер обновляет только время последней активности в чате. Текст и ключи для предпросмотра на сервер не передаются. Список переписок показывает нейтральное «Сообщение», когда последняя активность новее старой видимой истории, и не выводит устаревший текст старого сообщения за новое. VoiceOver получает актуальное время.
