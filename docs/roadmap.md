# Bulbam roadmap

Этот roadmap отвечает на вопрос **что мы строим дальше и в каком порядке**. Полная продуктовая идея, включая белорусскую идентичность, антифрод, бульбу, купоны и международный рост, находится в `docs/product-vision.md`.

Главное правило: новый слой не считается причиной бросить незавершённый фундамент предыдущего слоя.

## Текущий приоритет

Bulbam уже вышел дальше старого описания «только persistent direct messaging»: работают аккаунты, постоянные личные сообщения, realtime, Web Push и one-to-one аудиозвонки.

Сейчас приоритет — **довести ядро до состояния, которому можно доверять**, а не одновременно добавлять группы, истории, игры, Premium и каналы.

Порядок ближайших работ:

1. закончить delivery/read и multi-device сценарии;
2. укрепить auth/rate limiting и управление сессиями;
3. добавить медиа и голосовые через отдельное хранилище;
4. продолжать полевые тесты звонков и сетевой telemetry/recovery;
5. сделать блокировки, жалобы, антиспам и первый safety-фундамент;
6. только после этого группы и контролируемые каналы;
7. затем фирменный картофельный слой.

## Phase 0 — bootstrap — ГОТОВО

- [x] новый репозиторий без наследия Lenovo Messenger;
- [x] один Cloudflare Worker `bulbam-api`;
- [x] статический доступный web/PWA-клиент;
- [x] health/ready endpoints;
- [x] архитектурные правила;
- [x] модульный монолит с разделением domain/application/ports/infrastructure/transport.

## Phase 1 — accounts and sessions — ОСНОВА ГОТОВА

Цель: стабильная идентичность пользователя, не зависящая от отображаемого имени.

- [x] приглашения для тестеров;
- [x] регистрация одного аккаунта на приглашение;
- [x] стабильный `user_id`;
- [x] PBKDF2-хеширование пароля;
- [x] отдельные серверные сессии устройств;
- [x] вход и HttpOnly/Secure session cookie;
- [x] список активных сессий;
- [x] отзыв отдельной сессии устройства;
- [x] минимальный профиль: username и отображаемое имя;
- [ ] одна команда «выйти на всех устройствах»;
- [ ] отдельный rate-limit для auth/search и чувствительных маршрутов;
- [ ] пользовательское удаление аккаунта и понятный lifecycle данных;
- [ ] аватар профиля после появления media-модуля.

## Phase 2 — persistent direct messaging — РАБОТАЕТ, НУЖНО ДОБИТЬ

- [x] поиск человека по отображаемому имени и `@username`;
- [x] один стабильный личный диалог для пары пользователей;
- [x] серверное хранение сообщений в D1;
- [x] `client_message_id` и защита от дублей при retry;
- [x] состояния клиента `pending`, `sent`, `failed`;
- [x] серверное подтверждение доставки `delivered`;
- [ ] серверное состояние `read` и UI прочтения;
- [x] история после нового входа/перезагрузки;
- [x] офлайн-получатель получает накопленные сообщения;
- [x] восстановление после обрыва без дублей;
- [ ] полноценная пагинация старой истории;
- [ ] редактирование сообщений;
- [ ] удаление сообщений с чёткой серверной семантикой;
- [ ] ответы/reply;
- [ ] реакции;
- [ ] поиск по истории.

### Exit criteria Phase 2

Личный текстовый чат должен переживать reload, reconnect, повтор запроса, несколько устройств и временное отсутствие realtime без потери или дублирования сообщений.

## Phase 3 — realtime, multi-device and notifications — ЧАСТИЧНО ГОТОВО

- [x] per-user Durable Object + WebSocket;
- [x] живые события для подключённых устройств пользователя;
- [x] polling fallback при потере WebSocket;
- [x] Web Push для фоновых сообщений;
- [x] Web Push для входящего звонка;
- [x] service worker открывает/фокусирует нужный чат;
- [ ] курсор пропущенных realtime-событий после reconnect без полного refresh;
- [ ] отдельные регрессионные тесты нескольких устройств одного аккаунта;
- [ ] согласованная multi-device семантика read/delivered;
- [ ] presence/last seen;
- [ ] политика heartbeat и очистки устаревших realtime-соединений;
- [ ] пользовательские настройки уведомлений и privacy превью.

## Phase 4 — one-to-one audio calls — ПЕРВАЯ РАБОЧАЯ ВЕРСИЯ ГОТОВА

Звонки были реализованы раньше старого roadmap, потому что фундамент личных чатов уже позволил отделить CallRoom от постоянной истории.

- [x] one-to-one WebRTC audio;
- [x] отдельный CallRoom Durable Object;
- [x] offer/answer/ICE signaling;
- [x] STUN и поддержка TURN;
- [x] временные TURN credentials при соответствующей конфигурации;
- [x] входящий/исходящий звонок;
- [x] ответ, отклонение, завершение;
- [x] mute;
- [x] восстановление звонка после reload через явное действие пользователя;
- [x] автоматический ICE restart при сетевом сбое;
- [x] обновление STUN/TURN маршрутов при recovery;
- [x] hard rebuild peer connection как fallback;
- [x] адаптивное увеличение jitter buffer там, где браузер это поддерживает;
- [x] polling/realtime recovery сигналинга;
- [x] push входящего звонка;
- [ ] сетевой diagnostic/telemetry экран для тестеров: RTT, loss, jitter, selected candidate type;
- [ ] регрессионная матрица iPhone Safari, Android/Chrome, Mac Safari, Windows Chrome;
- [ ] тесты переключения Wi‑Fi/mobile и длительного плохого соединения;
- [ ] история звонков как отдельный durable слой, если она понадобится продукту;
- [ ] multi-device правила входящего звонка;
- [ ] видео только после доказанной устойчивости аудио.

### Exit criteria Phase 4

Нельзя рекламировать «идеальные звонки». Можно заявлять только поведение, подтверждённое полевыми тестами и regression suite.

## Phase 5 — media and voice messages

Медиа не передаются как inline/base64 через WebSocket.

- [ ] отдельный `media` domain;
- [ ] R2/object storage;
- [ ] безопасная upload-сессия;
- [ ] ограничения размера и типа;
- [ ] фотографии;
- [ ] документы;
- [ ] видео-файлы;
- [ ] голосовые сообщения;
- [ ] загрузка/докачка при плохой сети;
- [ ] медиа доступны после смены устройства;
- [ ] локальный кэш только как ускорение;
- [ ] доступный player голосовых;
- [ ] подготовка к Premium-транскрипции голосовых, но не раньше самих голосовых.

## Phase 6 — trust and safety

Это обязательный слой до большого публичного роста.

### Блокировки и жалобы

- [ ] блокировка пользователя;
- [ ] разблокировка;
- [ ] жалоба с причиной;
- [ ] защита от abuse массовыми жалобами;
- [ ] базовая модераторская очередь;
- [ ] accessible UX блокировки;
- [ ] фирменная «летящая бульба» только как необязательная анимация поверх реального действия.

### Антиспам

- [ ] rate limits по чувствительным операциям;
- [ ] ограничения новых/подозрительных аккаунтов;
- [ ] сигналы массовой одинаковой рассылки;
- [ ] безопасная эскалация без автоматического вечного бана по одному сигналу.

### Антифрод

- [ ] извлечение URL из сообщений;
- [ ] проверка известных threat feeds;
- [ ] безопасный изолированный анализ внешних URL;
- [ ] защита проверяющего сервиса от SSRF и внутренних адресов;
- [ ] оценка контекста сообщения;
- [ ] объяснимые причины предупреждения;
- [ ] уровни риска вместо бинарного «безопасно/мошенник»;
- [ ] быстрые действия «заблокировать» и «пожаловаться».

Никогда не показывать абсолютное «ссылка безопасна». Корректно: «известных признаков угрозы не обнаружено».

## Phase 7 — privacy and security model

До сильных публичных обещаний о конфиденциальности нужен отдельный threat model.

- [ ] описать, какие данные сервер должен видеть для работы продукта;
- [ ] определить модель шифрования личных сообщений;
- [ ] решить multi-device key management, если выбирается E2EE;
- [ ] решить восстановление аккаунта и потерянное устройство;
- [ ] privacy-настройки push-превью;
- [ ] политика хранения/удаления данных;
- [ ] security review протокола до маркетинговых заявлений.

Текущие текстовые сообщения нельзя называть end-to-end encrypted, пока сервер хранит читаемое тело сообщения.

## Phase 8 — groups

Только после устойчивых личных чатов, media и safety-фундамента.

- [ ] создание группы;
- [ ] участники;
- [ ] роли и права;
- [ ] приглашения/добавление/удаление;
- [ ] закреплённые сообщения;
- [ ] group media;
- [ ] групповые блокировки/жалобы;
- [ ] история и multi-device sync;
- [ ] accessibility больших списков участников.

## Phase 9 — controlled channels

Первая модель может быть закрытой и ручной.

- [ ] официальный канал Bulbam/Беларуси;
- [ ] областные и городские каналы;
- [ ] новости и спорт;
- [ ] каналы проверенных организаций/партнёров;
- [ ] заявка на создание стороннего канала;
- [ ] понятное значение статуса «официальный»;
- [ ] жалобы и модерация;
- [ ] позже роли доверия и масштабируемая система верификации.

Не открывать бесконтрольное массовое создание каналов до готового safety-модуля.

## Phase 10 — bots/platform

На старте боты остаются внутренними.

Позже, если продукт готов:

- [ ] bot API;
- [ ] permission model;
- [ ] sandbox;
- [ ] review сторонних приложений;
- [ ] отзыв токенов и разрешений;
- [ ] прозрачное отображение доступа к данным;
- [ ] лимиты и abuse prevention.

## Phase 11 — Bulbam identity

Только после крепкого коммуникационного ядра:

- [ ] картофельные presence-статусы как дополнительный стиль;
- [ ] стикеры Bulbam;
- [ ] виртуальные подарки;
- [ ] игровая валюта «бульбы» без денежного вывода на первом этапе;
- [ ] совместное выращивание бульбы с другом;
- [ ] достижения;
- [ ] фирменная анимация блокировки с Reduce Motion fallback;
- [ ] опциональный эксперимент фильтра ненормативной лексики;
- [ ] мини-игры про бульбу и блюда.

Точные правила «100 дней / 30 минут / 100 бульб» остаются гипотезой для прототипа, а не утверждённым балансом.

## Phase 12 — Premium

Premium не продаёт базовую безопасность.

Кандидаты:

- [ ] транскрипция голосовых;
- [ ] дополнительные иконки;
- [ ] расширенные стикеры/оформление;
- [ ] дополнительные виртуальные подарки;
- [ ] повышенные не-security лимиты.

Не утверждено:

- лимиты секретных чатов;
- любые ограничения криптографической защиты для бесплатных пользователей.

## Phase 13 — partners and regional ecosystem

Первый фокус — Беларусь.

- [ ] партнёрская модель;
- [ ] реальные купоны;
- [ ] разделение виртуальной валюты и реального купона;
- [ ] белорусские компании и локальные предложения;
- [ ] региональные новости/спорт/городские сервисы;
- [ ] правила маркировки рекламы и партнёрского предложения;
- [ ] защита от фальшивых купонов и партнёров.

## Phase 14 — international growth

Только если качество и реальный спрос это оправдывают.

- [ ] региональная конфигурация партнёров и купонов;
- [ ] локальные каналы и язык;
- [ ] возможные рынки: Россия, Польша, Литва, Германия, США и другие;
- [ ] единая сеть Bulbam без несовместимых национальных версий;
- [ ] белорусская картофельная идентичность сохраняется как происхождение бренда.

## Обязательные проверки каждого этапа

- Safari на iPhone;
- Safari на Mac;
- VoiceOver;
- клавиатурное управление;
- Android/Chrome и TalkBack для мобильных функций по мере их появления;
- Windows Chrome для сетевых и аудио сценариев;
- медленная/пропадающая сеть;
- переключение сети для realtime/звонков;
- reload во время операции;
- повтор операции не создаёт дубликат;
- постоянные данные переживают закрытие клиента;
- production-like smoke;
- регрессия на каждый установленный глубокий баг;
- маркетинговая формулировка не обещает больше, чем реально проверено.

## Правило выбора следующей задачи

Если одновременно есть:

- баг, из-за которого теряется связь/данные;
- незакрытая security/accessibility проблема;
- новая декоративная или игровая функция,

приоритет получает баг или security/accessibility работа.

Именно так Bulbam должен избежать ситуации «функций много, а базовое общение работает плохо».
