# Bulbam roadmap

## Phase 0 — bootstrap

- [x] Новый репозиторий без наследия Lenovo Messenger.
- [x] Один Cloudflare Worker `bulbam-api`.
- [x] Статический доступный веб-клиент.
- [x] `GET /api/health`.
- [x] Архитектурные правила и контракт сообщений.

## Phase 1 — accounts

Цель: стабильная идентичность пользователя, не зависящая от имени.

- [x] приглашения для тестеров;
- [x] регистрация одного аккаунта на приглашение;
- [x] стабильный `user_id` и отдельные серверные сессии устройств;
- [x] вход и безопасная серверная сессия;
- [x] выход/отзыв отдельной сессии устройства;
- [ ] одна команда «выйти на всех устройствах»;
- [x] минимальный профиль пользователя;
- [x] приглашения резко ограничивают открытую массовую регистрацию;
- [ ] отдельный rate-limit для перебора auth/search маршрутов.

D1 подключён и является постоянным источником истины для identity.

## Phase 2 — persistent direct messages — ТЕКУЩИЙ ЭТАП

- [x] поиск человека по отображаемому имени и `@username`;
- [x] создать/получить один личный диалог для пары пользователей;
- [x] серверное хранение сообщений в D1;
- [x] `client_message_id` для идемпотентной отправки;
- [x] клиентские состояния `pending`, `sent`, `failed`;
- [ ] серверные состояния `delivered`, `read`;
- [x] загрузка той же истории после нового входа/перезагрузки;
- [x] офлайн-получатель видит накопленные сообщения при следующем входе;
- [x] восстановление после обрыва без дублей: D1 + idempotency + polling fallback;
- [ ] пагинация старой истории;
- [x] воспроизводимый smoke: два аккаунта, поиск, 10 сообщений, история у обоих, duplicate retry.

## Phase 3 — realtime sync — ЧАСТИЧНО НАЧАТ

WebSocket начали раньше, потому что он уже полезен для Phase 2, но постоянные данные от него не зависят.

- [x] per-user Durable Object + WebSocket для живых событий;
- [x] одно событие нового сообщения приходит всем подключённым устройствам пользователя;
- [x] polling fallback при потере WebSocket;
- [ ] курсор событий и догрузка пропущенного после reconnect без полного refresh;
- [ ] отдельные тесты нескольких устройств одного аккаунта;
- [ ] presence/last seen;
- [ ] серверный heartbeat/политика очистки устаревших realtime-соединений.

## Phase 4 — media

- [ ] R2 для файлов;
- [ ] фотографии и документы;
- [ ] голосовые сообщения;
- [ ] безопасная загрузка и ограничения размеров;
- [ ] медиа остаются доступны после смены устройства;
- [ ] локальный кэш только как ускорение.

## Phase 5 — calls

Используем `MyMessenger` как лабораторию и переносим поведение, а не Swift-код.

- [ ] WebRTC signaling;
- [ ] ICE/STUN/TURN;
- [ ] Opus;
- [ ] адаптивный битрейт;
- [ ] обработка плохой сети;
- [ ] mute/output controls;
- [ ] состояния звонка и защита от stale signals;
- [ ] затем видео.

## Phase 6 — messenger features

- [ ] группы;
- [ ] каналы;
- [ ] блокировки;
- [ ] жалобы и антиспам;
- [ ] проверка подозрительных ссылок;
- [ ] редактирование/удаление сообщений;
- [ ] поиск по сообщениям;
- [ ] реакции и ответы.

## Phase 7 — Bulbam identity

Только после надёжного ядра:

- [ ] картофельные статусы;
- [ ] бульбы/подарки;
- [ ] выращивание картошки с друзьями;
- [ ] фирменные анимации блокировки;
- [ ] дополнительные premium-функции;
- [ ] эксперименты с заменой мата на «бульбу».

## Обязательные проверки каждого этапа

- Safari на iPhone;
- Safari на Mac;
- VoiceOver;
- клавиатурное управление;
- медленная/пропадающая сеть;
- перезагрузка страницы во время операции;
- повтор одной операции не создаёт дубликат;
- серверные данные переживают закрытие браузера;
- production smoke создаёт только временные `smoke_` аккаунты и удаляет их после проверки.
