# Архитектура Bulbam

Bulbam строится как модульный монолит. Это сознательный выбор: один deployable Worker и один репозиторий, но внутри — строгие границы доменов. Микросервисы не нужны, пока реальная нагрузка или независимое масштабирование не докажут обратное.

## Верхний уровень

- `web/` — web-клиент. Не содержит серверной бизнес-логики.
- `worker/src/index.ts` — только точка входа Cloudflare Worker.
- `worker/src/app.ts` — composition root: создаёт реализации зависимостей и соединяет модули.
- `worker/src/core/` — маленькие общие технические примитивы без бизнес-смысла: HTTP, ошибки, криптография.
- `worker/src/platform/` — контракты конкретной платформы исполнения (Cloudflare bindings).
- `worker/src/modules/` — бизнес-домены. Каждый домен владеет своей логикой и своими таблицами.

## Структура каждого бизнес-модуля

Пример: `modules/identity/`.

### `domain/`

Чистая модель предметной области: типы, значения, инварианты и валидация. Domain не импортирует Cloudflare, D1, HTTP, HTML и конкретные SDK.

### `application/`

Use cases приложения. Здесь решается *что* должно произойти: зарегистрировать пользователя, выдать сессию, создать приглашение. Application зависит от domain и от абстрактных портов, но не от SQL и не от HTTP.

### `ports/`

Интерфейсы зависимостей модуля: репозитории, очереди, внешние сервисы. Это граница между бизнес-логикой и инфраструктурой.

### `infrastructure/`

Конкретные адаптеры портов: D1, R2, Durable Objects, внешние API. SQL разрешён здесь и только здесь.

### `transport/`

HTTP/WebSocket/API-адаптеры. Они разбирают запрос, вызывают application service и превращают результат в ответ. Здесь запрещено писать бизнес-правила и SQL.

## Жёсткие правила зависимостей

1. `domain` не импортирует `application`, `transport`, `infrastructure`, `platform`.
2. `application` не импортирует `transport` или конкретную инфраструктуру.
3. `transport` не обращается к D1/R2 напрямую.
4. SQL не живёт вне `infrastructure`.
5. `index.ts` не превращается в роутер и не содержит бизнес-логику.
6. `app.ts` только собирает зависимости; доменные решения туда не переносятся.
7. Один модуль не импортирует внутренний `infrastructure/` другого модуля.
8. Общий `core/` не становится свалкой. Если код имеет бизнес-смысл только для одного домена — он остаётся в этом домене.
9. Каждая таблица имеет владельца-модуль. Схему другой области нельзя менять молча из чужого модуля.
10. Внешние идентификаторы и отображаемые имена не заменяют внутренние UUID.

## План доменов

Сейчас:

- `identity` — аккаунты, приглашения, роли, сессии устройств.

Следующие независимые модули:

- `messaging` — диалоги, сообщения, idempotency, delivery/read receipts;
- `media` — метаданные вложений и R2;
- `presence` — online/last seen и будущие картофельные статусы;
- `realtime` — доставка живых событий/WebSocket, но не постоянное хранение сообщений;
- `calling` — сигналинг WebRTC/LiveKit и профили звонков;
- `groups` — группы и членство;
- `channels` — каналы/подписки;
- `safety` — блокировки, жалобы, анализ подозрительного контента;
- `billing` — будущий Premium, если он появится.

Названия модулей — не обещание реализовать всё сразу. Они фиксируют границы, чтобы функции не разрастались в один MessengerService.

## Данные

D1 — постоянный источник истины для структурированных данных первой версии. Каждый модуль ведёт собственные версионированные миграции. Изменения схемы должны быть обратимо/пошагово разворачиваемыми; нельзя рассчитывать, что все клиенты обновились одновременно.

Медиа позже хранятся отдельно от сообщений. Сообщение хранит ссылку/идентификатор медиа и метаданные, а не base64-файл внутри WebSocket-события.

## Realtime

WebSocket/Durable Object — транспорт живых событий, а не единственная память системы. Если все браузеры закрылись, аккаунты, сообщения, статусы доставки и важные операции не должны исчезнуть.

## Клиент

Web-клиент тоже должен дробиться по функциям по мере роста. Пока Phase 1 мала, допустим один `app.js`; до добавления полноценного messaging UI его нужно разнести на модули (`api`, `auth`, `sessions`, `ui`). Нельзя ждать, пока один файл станет тысячей строк.

## Тестирование границ

Минимум для каждого нового модуля:

1. unit-тест application/domain без Cloudflare;
2. интеграционный тест инфраструктуры/HTTP там, где есть постоянное состояние;
3. регрессия на каждый найденный глубокий баг;
4. smoke-проверка production-like Worker перед слиянием крупной фазы.

Если для новой функции приходится импортировать половину проекта, это считается архитектурным дефектом, а не удобством.
