# Групповые чаты Бульбама

## Первая реализация

Группы используют существующие личные переписки как часть общей модели `Conversation`.
Текстовые и голосовые сообщения, WebSocket, HTTP polling, пуши и хранение остаются в общем
конвейере. Групповые аудиозвонки ещё не поддерживаются; личный звонок доступен только
для `kind: direct`.

Создание: «Новый чат» → «Создать группу». Пользователь вводит название, выбирает один из
готовых значков, отмечает участников из существующих личных чатов или находит их через
поиск зарегистрированных пользователей. Добавление прямое, без подтверждения приглашения.

Создатель видит список участников и может добавить новых или исключить имеющихся.
Обычный участник может выйти сам. Создатель пока не может выйти, пока не появится
передача прав или удаление группы. Система «Варта», закрепления, роли модераторов и
групповые звонки не входят в этот выпуск.

## Архитектура и база

V4 миграции messaging переименовывает `direct_conversations` в `conversations`, сохраняя
существующие личные беседы и автоматически обновляя внешний ключ `messages` средствами
SQLite. В общей таблице `kind=direct|group`, `title`, `owner_user_id`, `history_mode`,
`avatar_icon`. Два legacy `participant_*_id` остаются в схеме для существующих личных
бесед. Для групп они не являются источником полномочий: фактическое членство определяется
**только** отдельной таблицей `group_members(user_id, joined_at)`.

Базовая политика выбирается создателем при создании группы:

- `all`: добавленные позднее видят прежнюю переписку.
- `since_join`: новые участники получают только сообщения от своего `joined_at`;
  время добавления также должно быть позднее последнего сохранённого сообщения.

Ограничение проверяется **на сервере** для списка сообщений, отметок доставки и прочтения,
запросов аудио и прогресса прослушивания. Скрытие в интерфейсе само по себе не считается
защитой. При выходе пользователь перестаёт получать новые данные; уже ранее загруженные
на его устройство данные нельзя криптографически отозвать, поскольку E2EE ещё не введено.

## API

- `POST /api/v1/chats/groups`:
  `{title, avatarIcon, historyMode:"all"|"since_join", userIds:[uuid,...]}`; HTTP 201.
  Название 1–80 символов, участников кроме создателя 1–99, значок из списка.
- `GET /api/v1/chats`: личные и групповые беседы, `kind` явно указан в ответе.
- `GET /api/v1/chats/{id}/members`: участники и публичные имена, только члену группы.
- `POST /api/v1/chats/{id}/members`: `{userIds:[...]}`, только создатель, максимум 100 участников.
- `DELETE /api/v1/chats/{id}/members/{userId}`: самостоятельный выход либо исключение
  создателем. Нельзя удалить создателя.
- Существующие `GET|POST /api/v1/chats/{id}/messages` и `/receipts/read|delivered`,
  а также endpoints голосового, работают для обеих разновидностей беседы.

Отметка прочтения сохраняется отдельно для каждого пользователя в `message_receipts`.
Собственные сообщения отправителя в групповом `GET /messages` содержат массив `readBy`
и число ожидаемых получателей `eligibleRecipientCount`, вычисленное с учётом политики
доступа к истории. В интерфейсе видны «Прочитали: N из M» и раскрываемый список имён.

`GET /api/v1/presence` возвращает присутствие существующих личных собеседников **или**
других участников общих групп, но учитывает настройку скрытия активности. Клиент в
заголовке группы показывает количество пользователей, находящихся в сети.

Realtime `chat.created`, `chat.updated`, `chat.removed` обновляют список чатов.
`message.created` и индивидуальные `messages.read` используют прежние механизмы.
Push-уведомления для групп содержат название группы и имя автора; уведомления и
realtime новых сообщений не отправляются участнику, которому это сообщение недоступно
из-за времени добавления.

## Ограничения и проверки

Пока нет сквозного шифрования, групповых вызовов, переноса владения, ролей «Варта»,
массовых файлов и сложной модерации. UI для голосовых переиспользует работающий
рекордер и проигрыватель без замены их VoiceOver поведения. Звонки 1:1 не менялись.

Интеграционные тесты `test/group-chats-smoke.test.js` запускают Worker c D1 и Durable
Objects, создают настоящие тестовые сессии, проверяют обе политики истории, независимое
прочтение, членство, ограничения, реальный upload голосового через WebSocket и HTTP Range
для авторизованного участника при отказе постороннему. Полный `npm run verify` включает
также регрессионные проверки личных сообщений, звонков и белорусской локализации.

Фактическое поведение VoiceOver и визуальный мобильный вид на iPhone/Android требуют
дополнительных приёмочных испытаний на физических устройствах.
