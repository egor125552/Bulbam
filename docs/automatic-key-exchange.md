# Автоматический обмен ключами, первый экспериментальный выпуск

## Как пользоваться

В личном чате открыть «Защита» → «Включить автоматическую защиту» на первом устройстве аккаунта. Подтвердить предупреждение об ограничениях. Второй участник делает то же самое **на своём** устройстве. Бульбам сам публикует открытые ECDH P-256 ключи и согласовывает AES-256-GCM ключ переписки локально. Общий секрет не передаётся серверу или через чат. Если второй человек ещё не включил функцию, отправка на первом устройстве блокируется. После регистрации обоих сервер атомарно закрепляет `encryption_mode=protected`, `auto_protection=1` и запрещает открытые новые текстовые и голосовые сообщения даже старым клиентам.

Если второй участник ещё не зарегистрировал ключ, кнопка «Повторить автоматический обмен» проверит готовность. Повторный просмотр чата и событие `chat.updated` запускают проверку. Для ручного режима, включённого ранее, автоматическая миграция запрещена, потому что она нарушила бы доступ к уже зашифрованной истории.

## Как это работает

- На устройстве создаётся неэкспортируемый приватный `CryptoKey` для ECDH P-256. Он хранится **только локально** в IndexedDB. Публичная часть в формате JWK публикуется через аутентифицированный `PUT /api/v1/keys/identity`.
- Сервер запоминает **первый** публичный ключ аккаунта и запрещает его молчаливую замену даже при другом действительном сеансе. Запрос открытых ключей разрешён только участнику личной беседы. Пара ключей не отправляется вместе с сообщением.
- Браузер получает публичный ключ собеседника, запоминает его при первом обращении (TOFU) и блокирует дальнейший обмен при изменении. Затем обе стороны независимо вычисляют общий секрет через ECDH и выводят неэкспортируемый AES-GCM ключ через HKDF-SHA-256 с привязкой к ID разговора и двум аккаунтам.
- Существующие форматы зашифрованных сообщений и голосовых используются без изменения. Шифрование выполняется только браузером. Триггер D1 дополнительно запрещает вставку обычного текста в защищённую личную переписку.

## Нельзя выдавать это за Signal

Это **не** Signal Protocol. Нет Double Ratchet, прямой секретности, post-compromise security, криптографической подписи авторства, независимого аудита, прозрачного лога ключей и достоверной идентификации человека при *первом* получении его ключа. Сервер, злонамеренный при первом обмене, потенциально способен подменить ключ, а позднейшие подмены блокируются локально. Заражённый клиент или загрузка модифицированного JavaScript тоже могут перехватить данные до шифрования.

**Особенно важно:** пока поддерживается **только первое зарегистрированное устройство аккаунта**. Вход на другом iPhone/Mac не копирует приватный ключ; попытка создать другой ключ приводит к ошибке, а защищённая история недоступна. Если IndexedDB первого устройства очищен или устройство утеряно, без будущего механизма переноса его ключ не восстановить. Не включайте функцию для важных переписок, если нужен надёжный доступ с нескольких устройств или гарантированное восстановление. Перед включением есть подтверждение этого ограничения. Следующий необходимый этап: безопасное подтверждённое подключение дополнительных устройств и многополучательские ключи, затем независимый security review.

Группы, звонки, старые сообщения, метаданные, push-адреса и локальные незашифрованные черновики не становятся автоматически защищёнными.

## Уведомления

Сообщения теперь направляются в push-сервис всем подписанным устройствам, а Service Worker подавляет дубликат только на устройстве, где окно Бульбама действительно видно. Старая глобальная отметка foreground могла подавить уведомление на iPhone из-за открытой вкладки на другом устройстве. В настройках есть «Проверить доставку уведомлений»: API `POST /api/v1/push/test` сообщает число подписок и число принятых push-сервисами запросов. Принятие push-сервисом **не гарантирует** отображение системой. На iPhone Safari нужно добавить сайт на экран «Домой» и открыть как веб-приложение, затем разрешить уведомления в iOS и в Бульбаме. Реальную доставку следует отдельно проверить на устройстве.
