# Голосовые сообщения Bulbam

Этот документ фиксирует фундамент голосовых сообщений версии 0.6. Расшифровка речи в этот этап не входит.

## Пользовательское поведение

Обычная кнопка «Записать голосовое» запускает запись. Повторное нажатие останавливает запись и сразу отправляет её. Паузы внутри записи нет. Escape отменяет текущую запись без отправки.

На Mac есть дополнительный быстрый способ: удержание Option запускает запись после короткой задержки, отпускание Option останавливает и отправляет. Control+Option и другие сочетания не должны запускать голосовое, чтобы не конфликтовать с VoiceOver. Потеря фокуса окна во время записи через Option считается прерыванием: запись сохраняется локально и сама не отправляется.

Начало, успешная остановка, отмена и ошибка имеют разные короткие звуковые сигналы и понятные live-объявления для экранного диктора. Сигнал начала полностью заканчивается до запуска MediaRecorder; сигнал остановки или отмены звучит только после остановки микрофона, поэтому Bulbam не должен сам записывать свои служебные сигналы.

Во время активного аудиозвонка новая запись голосового блокируется, чтобы два независимых захвата микрофона не ломали друг другу звук.

## Запись

Голосовые записываются только в Opus, если браузер действительно поддерживает Opus через MediaRecorder. Эхоподавление, шумоподавление и автоматическая регулировка громкости запрашиваются выключенными. Если браузер явно сообщает, что обработка осталась включена, Bulbam не выдаёт такую запись за необработанную и сообщает об ошибке.

Доступные битрейты: 24, 32, 48, 64 и 96 кбит/с. Значение по умолчанию — 64 кбит/с. Качество хранится отдельно на каждом устройстве и не зависит от профилей микрофона звонков.

Жёсткого пользовательского ограничения длительности нет. Фактический предел определяется свободным локальным местом, возможностями браузера и доступным серверным хранилищем.

## Защита записи от потери

MediaRecorder выдаёт небольшие куски примерно раз в секунду. Каждый кусок сразу сохраняется в IndexedDB. Поэтому длинное голосовое не существует только как один объект в оперативной памяти.

Если вкладка была выгружена, браузер завершил микрофон, устройство потеряло фокус во время Option-записи или произошла другая авария, уже записанная часть остаётся локальным черновиком. Она не отправляется автоматически. Пользователь может позже отправить или удалить её.

Фоновая запись является best-effort: Bulbam продолжает запись, пока браузер и операционная система сохраняют захват микрофона. Нельзя обещать, что мобильная система никогда не остановит web-приложение при блокировке экрана или нехватке ресурсов.

## Доставка и серверное хранение

Для текущего бесплатного прототипа Bulbam не требует R2 и не требует отдельного платёжного файлового сервиса. Основная D1 хранит только сообщения, аккаунты, чеки доставки и метаданные голосовых. Аудиобайты вынесены из неё.

Для каждой отправляемой записи создаётся отдельный `VoiceUploadRoom` Durable Object. Этот объект выполняет сразу две связанные задачи: принимает бинарные части через отдельный WebSocket и хранит подтверждённые части в собственном SQLite-backed Durable Object storage.

Загрузка аудио не идёт через основной realtime WebSocket чата. Поэтому длинное голосовое не должно забивать канал, через который приходят текстовые сообщения, статусы и события звонков.

Клиент режет запись на части по 256 KiB. Бинарный WebSocket frame содержит четырёхбайтовый номер части и затем сами байты Opus. `VoiceUploadRoom` отвечает `voice.upload.ack` только после того, как часть записана в постоянное storage этого объекта.

При переподключении новый WebSocket получает список уже сохранённых частей. Клиент догружает только отсутствующие части. Поэтому краткий обрыв сети не должен заставлять заново передавать всё длинное голосовое.

Сервер не считает часть дубликатом только по её размеру. Если тот же номер части приходит повторно, сохранённые и новые байты должны совпасть. Иначе сервер возвращает конфликт.

Все обычные части имеют размер ровно 256 KiB. Часть меньшего размера считается хвостом записи и после неё сервер не принимает части с большими номерами. Благодаря этому byte-range остаётся однозначным и перемотка не зависит от недоверенных размеров, присланных клиентом.

Перед созданием сообщения финализация проверяет непрерывную нумерацию частей и итоговый размер. Только после этого media-состояние становится `ready`, и сообщение публикуется собеседнику.

Незавершённая серверная сессия не должна жить вечно. `VoiceUploadRoom` использует alarm: если в загрузку семь дней не приходило новых данных, её storage очищается. Если активность была позже, alarm переносит очистку относительно последней принятой части. Уже завершённые голосовые этим механизмом не удаляются.

## Почему Durable Object storage

Эта схема не расходует 500 MB лимита основной Free D1 на аудиофайлы и лучше соответствует самому протоколу: каждый голосовой объект уже имеет отдельный Durable Object для WebSocket-координации, поэтому его байты хранятся рядом с этой координацией.

Storage остаётся заменяемым слоем. Если Bulbam вырастет за бесплатный объём Durable Objects, медиа можно перенести в объектное хранилище без переделки MediaRecorder, модели сообщений, проигрывателя и пользовательских статусов.

## Прослушивание

Аудио выдаётся только участнику соответствующего диалога. Проигрывание не требует, чтобы отправитель был онлайн: после отправки части лежат в постоянном storage соответствующего `VoiceUploadRoom`.

Для проигрывания используется авторизованный HTTP endpoint с поддержкой Range. Worker сначала проверяет участие пользователя в диалоге, затем обращается к нужному Durable Object. Сам объект читает только требуемые чанки и выдаёт поток; всё голосовое не должно собираться целиком в памяти Worker или Durable Object.

Такой путь подходит для seek и для обычного браузерного media element лучше, чем попытка воспроизводить сохранённое сообщение через постоянно открытый WebSocket.

Проигрыватель имеет:

- воспроизведение и паузу;
- назад на 15 секунд;
- вперёд на 15 секунд;
- скорости 1×, 1,5× и 2×;
- доступный range-контрол с текущим временем и полной длительностью;
- объявление буферизации и продолжения;
- автоматический запуск только следующего голосового, если между сообщениями нет текста или другого типа сообщения;
- небольшую предварительную загрузку начала следующего голосового на любой сети.

Последняя скорость сохраняется на устройстве.

После полного первого прослушивания Bulbam пытается сохранить голосовое в ограниченный per-account Cache Storage. Старые элементы вытесняются; серверный `VoiceUploadRoom` остаётся источником истины. Кэш аккаунта удаляется при выходе из него.

## Прогресс прослушивания

Bulbam считает не максимальную позицию ползунка, а реально воспроизведённые интервалы аудио. Перемотка вперёд сама по себе не увеличивает «прослушано».

Клиент отправляет объединённые интервалы примерно раз в пять секунд, а также при паузе и завершении. Сервер повторно объединяет интервалы, поэтому повторное прослушивание того же участка не удваивает время. Сервер хранит личную позицию продолжения и отметку полного прослушивания.

Отправитель может видеть:

- «Сейчас слушает ваше голосовое»;
- «Прослушано 42 секунды»;
- «Прослушано полностью».

Живой статус имеет короткий срок жизни и не должен оставаться «слушает» после пропажи heartbeat.

Настройка «Показывать собеседникам прослушивание голосовых» включена по умолчанию. Если она выключена, личный resume-прогресс продолжает сохраняться для самого слушателя, но отправителю история и realtime не раскрывают подробный прогресс.

## Доступность

Основной сценарий не требует удержания кнопки. Удержание Option — дополнительный способ только на Mac. Все основные действия являются обычными HTML-кнопками с понятными названиями.

Для проверки VoiceOver недостаточно автоматических тестов. Перед слиянием нужно руками проверить: старт/стоп/отмену кнопкой; Option без VoiceOver; Control+Option с VoiceOver; потерю фокуса; восстановление прерванного черновика; 15-секундную перемотку; изменение скорости; буферизацию; цепочку нескольких голосовых.

## Что проверяют автоматические тесты

Smoke-тест проверяет серверный путь: создание сессии, бинарную WebSocket-загрузку в storage Durable Object, ACK после сохранения, разрыв и повторное подключение, восстановление списка уже принятых частей, status endpoint, запрет чужому участнику захватывать upload socket, побайтовый конфликт повторной части, запрет данных после короткого хвоста, финализацию, повторную безопасную финализацию, отсутствие старых таблиц аудиобайтов в основной D1, полный и Range-read через границу чанков, ответ 416 на некорректный Range, уникально прослушанные интервалы, приватность прогресса и запрет автору подделывать прослушивание собственного голосового.

Автоматические тесты не подтверждают реальное качество MediaRecorder на конкретном iPhone, продолжение записи при заблокированном экране, поведение Safari при нехватке памяти, звук системных сигналов, работу VoiceOver и реальную мобильную сеть. Эти сценарии остаются обязательной ручной проверкой.
