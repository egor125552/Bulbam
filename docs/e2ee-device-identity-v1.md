# Второе поколение E2EE: устройства, первый реализованный этап

Состояние: **новый реестр устройств и подтверждение ключей готовы, новый протокол сообщений НЕ включён**. Старые личные переписки всё ещё используют прежний ручной AES-GCM или долговременный ключ ECDH первого устройства, если пользователь включал его ранее. Этот этап не добавляет Double Ratchet, PQXDH, защиту групп или совместимость с Signal. Не маркируйте его как полностью работающий Signal Protocol.

## Что уже работает

- При входе Бульбам автоматически создаёт **отдельную** пару P-256 ECDSA (идентичность) и две пары P-256 ECDH (идентичность и подписанный prekey) на **каждом устройстве**. Приватные CryptoKey создаются как неэкспортируемые и сохраняются только в IndexedDB текущего браузера. На сервер отправляются исключительно открытые ключи и подписи. Алгоритм и формат данных привязаны к `bulbam/device-prekey/v1` и `bulbam/device-registration/v1`, userId и deviceId.
- Сервер криптографически проверяет регистрацию ключа и подпись prekey. Первый ключ аккаунта получает статус `active` по принципу TOFU, следующие получают `pending`. Запросы с тем же deviceId, но другими ключами, и повторная регистрация отозванного устройства отклоняются.
- Уже доверенное устройство может одобрить другое через `bulbam/device-approval/v1` с собственной подписью ECDSA. Сервер не допускает одобрения, если подписавшее устройство не имеет статуса `active`. Подмена идентичности ожидающего устройства делает подпись недействительной. Отзыв через `bulbam/device-revoke/v1` тоже требует действительной подписи **другого** активного устройства; нельзя отозвать последнее активное.
- В разделе «Устройства» есть новый подраздел «Ключи устройств», автоматически показывающий локальную регистрацию, ожидающие и доверенные устройства, а также доступные владельцу доверенного ключа кнопки подтверждения/отзыва. Элементы доступны с VoiceOver.
- Директория открытых ключей собеседника доступна только участникам конкретного **личного** чата. Она выдаёт только доверенные устройства, не выдаёт `pending` или `revoked`, приватные ключи и секреты на сервер никогда не поступают.

## Контракты API

Требуют обычной авторизованной сессии, все изменения идентичности дополнительно проверяют криптографические подписи.

- `POST /api/v1/e2ee/devices`: `{deviceId,identitySigning,identityAgreement,signedPrekey,prekeySignature,registrationSignature}` → `{ok,device:{trust}}`; неизменяемая регистрация.
- `GET /api/v1/e2ee/devices` → `{ok,devices:[...]}` включая pending и revoked только для собственного аккаунта.
- `POST /api/v1/e2ee/devices/approve`: `{approverDeviceId,newDeviceId,signature}` → `{ok,approvedDeviceId}` после подписи trusted device.
- `POST /api/v1/e2ee/devices/revoke`: `{approverDeviceId,deviceId,signature}` → `{ok,revokedDeviceId}` после подписи другого активного устройства.
- `GET /api/v1/chats/{conversationId}/e2ee/devices` → `{ok,users:[{userId,devices:[...]},...]}` только активные публичные ключи участников личного чата.

## Граница доверия

Первый активный ключ основан на **первом успешном входе** и всё ещё уязвим при захвате аккаунта до первой регистрации. Даже подтверждённый дополнительный ключ **пока не подключает его к историческим сообщениям**: новая криптографическая транспортная система ещё не внедрена. Защита от доставки подложных ключей зависит от доверия первому устройству, локального хранения и будущих safety numbers/transparency log. Открытое веб-приложение также зависит от подлинности загружаемого JavaScript, который контролирует сервер. В случае утраты всех активных приватных ключей нельзя автоматически повысить новое устройство, иначе злоумышленник с украденным паролем получит всю будущую E2EE переписку.

## Следующий этап

Интегрировать проверенную реализацию PQXDH / Double Ratchet, провести аудит её браузерной совместимости и устойчивости. Добавить одноразовые prekeys, атомарную выдачу и потребление prekeys, отдельные ciphertext-конверты каждому устройству, доступную проверку подлинности ключей, безопасный перенос ключей/восстановление и безопасную миграцию `bmsec1`/`bmvoice1` без выдачи plaintext. Для iPhone Safari нужны настоящие device-тесты и испытания после очистки хранилища.
