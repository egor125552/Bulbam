# AccessPilot. Автономное исследование доступности Бульбама

AccessPilot запускает **настоящие обработчики навигации** Бульбама в
изолированном виртуальном HTML-документе. Физическое окно не открывается.
Тестировщик сам находит кнопки разделов, пробует переходить по ним и
собирает сведения о названиях элементов, их состоянии и происхождении
в исходном коде.

Запуск из корня проекта после `npm install --legacy-peer-deps`:

```sh
npm run test:accessibility
```

Отчёты создаются в папке `accesspilot-report`:
`Отчёт доступности Бульбама.txt` и
`Отчёт доступности Бульбама.json`.
Папка не отправляется в GitHub.

## Что выполняется

- Проверяются главный экран, категории настроек и вложенные страницы.
- Переходы находятся автоматически: нет заранее записанного маршрута
  на каждую категорию.
- Для каждой кнопки и поля выводятся название, роль, состояние и, где
  возможно, место создания элемента и регистрации обработчика нажатия.
- Нажатия открывающих, закрывающих и возвращающих кнопок запускают
  настоящие функции интерфейса, результат записывается в отчёт.
- Находятся пустые доступные имена, неправильные ссылки
  `aria-labelledby`, положительный `tabindex` и некоторые ошибки
  нестандартных кнопок.
- Действия изменения аккаунта, отправки сообщений, звонков и удаления
  данных не выполняются. Для них создаётся только запись об элементе.

## Чего тест НЕ обещает

Это **виртуальная проверка DOM**, а не запись настоящего VoiceOver.
Фразы в поле `predictedAnnouncement` являются приближённым
представлением данных доступности; скринридер может говорить иначе.
Виртуальная среда не выполняет CSS-раскладку, сетевые операции,
реальные аудио- и телефонные функции, проверку фокуса настоящего
браузера или поток живой речи VoiceOver. Сюда не входят полные сценарии
авторизации и переписки. Неактивированные кнопки нельзя считать
функционально проверенными. Отсутствие найденных ошибок не означает,
что программа полностью доступна.

## Архитектура

`engine.js` — универсальный автономный обход с ограничениями числа
экранов, глубины и нажатий. Не знает о Бульбаме и его кнопках.

`dom.js` — анализ доступных названий и состояний элементов без
зависимости от конкретного приложения.

`bulbam-adapter.js` — отдельная тестовая среда Бульбама: загружает
реальный HTML, подключает существующие обработчики, подменяет только
недоступные в виртуальном DOM функции окна и помечает безопасные
переходы. Никакого подключения к серверу и токенов нет.

`run.js` — запуск и текстовые/JSON-отчёты.

Для поддержки других программ достаточно написать свой адаптер.
Каждая среда может предоставлять больше достоверных сведений,
например данные настоящего браузерного дерева доступности.

## Расширенный обход

Второй этап проверки добавил самостоятельные безопасные маршруты
входа, регистрации, восстановления аккаунта и раскрытия поиска нового чата.
Форма отправки сообщения исследуется только в синтетическом состоянии,
**не отправляя сообщение и не создавая реального чата**.

Теперь отчёт отдельно показывает состояния фокуса после действий:
на какой элемент его перевёл обработчик и не оказался ли он скрыт.
Такие результаты являются моделированием браузерного фокуса, а не
проверкой настоящего VoiceOver.

Обнаруженная ошибка: после закрытия поиска нового чата фокус
оставался на скрытом поле ввода. Исправлено в `web/js/messenger.js`:
когда пользователь закрывает поиск повторным нажатием или Escape,
фокус возвращается на кнопку Новый чат. Программная смена аккаунта
не перехватывает фокус.

Отчёт хранит отдельные результаты каждого сценария.
Общее число проверок включает повторения одного элемента на разных экранах
и не означает число уникальных элементов приложения.

## Универсальный обход реального браузера

Основная команда `npm run test:accessibility` запускает **Chromium без
видимого окна** и настоящий Бульбам на изолированном тестовом сервере.
Перед первой проверкой на новом компьютере установите браузер:
`npx playwright install chromium`. Для старой виртуальной проверки
настроек существует `npm run test:accessibility:virtual`.

Обход не содержит списка кнопок Бульбама. Он находит все видимые
кнопки, ссылки, поля ввода, переключатели, раскрывающиеся элементы
и варианты списков. Вводит безвредные тестовые значения, выполняет
действия через браузер и сравнивает доступные состояния до и после.
Разделы обнаруживаются по фактическим изменениям структуры.
Это отдельный модуль, в который можно подставить другой адрес сайта.

Специальная часть Бульбама нужна **не для описания каждой кнопки**, а
исключительно для подъёма собственной временной тестовой базы с
вымышленными аккаунтами. Во время проверки приложение делает запросы
только к локальному серверу. Внешние запросы браузера блокируются.
Данные не попадают в действующую базу Бульбама.

Файлы:
- `tools/accesspilot/browser-engine.js`: универсальное исследование;
- `tools/accesspilot/browser-instrumentation.js`: регистрация места
  создания элементов и обработчиков событий;
- `tools/accesspilot/browser-host.js`: изолированный тестовый сервер;
- `tools/accesspilot/run-browser.js`: запуск, обход и отчёты.

Используется настоящее дерево доступности Chromium, но **не реальная
речь VoiceOver**. Автоматическое исполнение события ещё не доказывает,
что функция полностью правильно работает. Проверка записи звука,
полноценного WebRTC-звонка, системных разрешений и озвучки Safari
потребует дополнительных тестовых возможностей.

Есть лимиты на число исследуемых состояний и действий для защиты
от бесконечных циклов. Если отчёт показывает `truncated: true`,
проверка не полная; запустите снова с увеличенными лимитами:
`ACCESSPILOT_MAX_ACTIONS=300 ACCESSPILOT_MAX_STATES=100 npm run test:accessibility`.

## Мобильная ширина

Для проверки мобильной компоновки можно установить переменную
`ACCESSPILOT_MOBILE=1`. Тогда браузер выполняет те же автоматические
действия на экране шириной 390 пикселей с имитацией касаний.
Это НЕ эмулятор VoiceOver и НЕ настоящий Safari.

## Полный обход без ручного списка действий

`ACCESSPILOT_EXHAUSTIVE=1 npm run test:accessibility` увеличивает
допустимое число состояний, действий и глубину обхода. Исследователь
продолжает находить элементы автоматически; никакие новые
инструкции для кнопок писать не требуется.

Даже этот режим не гарантирует полного покрытия. Недостижимые
без реальных устройств, разрешений или тестовых данных действия
должны отмечаться непроверенными, а не успешными. Если ограничения
снова достигнуты, отчёт покажет незавершённые маршруты.

## Возобновление полного обхода

При больших интерфейсах выполненные действия и очередь оставшихся
разделов сохраняются автоматически в  `accesspilot-report/checkpoint-*.json`.
Можно продолжить проверку следующей порцией без повторной работы:

```sh
ACCESSPILOT_RESUME=1 ACCESSPILOT_EXHAUSTIVE=1 ACCESSPILOT_BATCH_ACTIONS=200 npm run test:accessibility
```

Для продолжения только после входа в тестовый аккаунт:

```sh
ACCESSPILOT_SCENARIOS=signed-in ACCESSPILOT_RESUME=1 ACCESSPILOT_EXHAUSTIVE=1 ACCESSPILOT_BATCH_ACTIONS=200 npm run test:accessibility
```

В отчёте `truncated: false` и `pending: 0` означают, что все
обнаруженные в этом сценарии маршруты обработаны. Это всё ещё не
подтверждает действия, требующие настоящей камеры, микрофона, второго
устройства, платежа или внешнего сервиса. Серверные данные каждого
отдельного запуска временные; длительная серия с контрольной точкой
восстанавливает последовательность браузерных действий, но не историю
серверных данных между запусками.

## Изолированная проверка звонков и сообщений

При запуске с `ACCESSPILOT_FAKE_MEDIA=1` браузер получает
искусственный микрофон Chromium, причём WebRTC UDP вне проксируемого
окружения блокируется. В тестовой базе автоматически создаются два
фиктивных пользователя, переписка и одно текстовое сообщение.
Эти данные нужны для появления соответствующих кнопок, **без ручной
карты действий**.

```sh
ACCESSPILOT_SCENARIOS=signed-in ACCESSPILOT_FAKE_MEDIA=1 ACCESSPILOT_EXHAUSTIVE=1 npm run test:accessibility
```

Отдельный отчёт `Покрытие элементов Бульбама.json` показывает,
какие статические элементы вообще появились на проверенных экранах,
для каких было вызвано действие и какие ещё не проверены. Если
в отчёте есть `blockedRoutes`, часть путей не удалось восстановить;
`complete` в этом случае равно `false`, даже если очередь обхода пуста.
Обход с реальным голосовым устройством, физическим iPhone и настоящим
VoiceOver остаётся отдельной проверкой.

## Переход в подраздел немедленно после нажатия

Исследователь теперь по умолчанию использует **обход в глубину**:
сразу после нажатия он проверяет появившийся экран, пока тот реально
открыт. Это важно для состояний звонка и записи, которые невозможно
безопасно воспроизводить повторно на том же тестовом аккаунте.
Поведение проверено на отдельной тестовой странице с одноразово
открывающейся кнопкой. Для сравнительной старой проверки в ширину
можно использовать переменную `ACCESSPILOT_BREADTH_FIRST=1`.
Контрольные точки этих двух режимов хранятся отдельно.
