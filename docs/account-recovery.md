# Вход, регистрация и восстановление аккаунта

## Навигация

Стартовый экран содержит только вход. Регистрация и «Забыли пароль?» открываются отдельными кнопками. После регистрации пользователь **сразу авторизован**, поскольку сервер создаёт сессию и отправляет защищённую HttpOnly-cookie. После успешного восстановления резервным кодом вход тоже выполняется автоматически.

Если проверка текущего сеанса ответила HTTP 401, интерфейс честно сообщает, что вход завершён или истёк, а не что аккаунт удалён. При временной ошибке сети прежнее состояние авторизации не стирается.

## Два самостоятельно доступных способа восстановления

1. **Резервный код.** На регистрации пользователь один раз получает восемь кодов вида `BRC-XXXXXX-XXXXXX-XXXXXX-XXXXXX`. Каждый содержит 96 бит криптографической случайности. Сервер записывает только хеш SHA-256. Восстановление через `POST /api/v1/auth/reset-with-recovery-code` требует имени, кода и нового пароля. Одна D1-транзакция меняет хеш пароля, отзывает все предыдущие сеансы и делает весь старый набор кодов недействительным. Затем выдаёт новую сессию и новый комплект кодов для сохранения. Код не отправляется по email и не хранится в доступном повторно виде.
2. **Другое устройство с действующим сеансом.** Откройте Настройки → Безопасность аккаунта → Сменить пароль. Пароль меняется без знания старого, поскольку пользователь уже аутентифицирован действующей сессией. Другие устройства и старые коды отключаются. После этого обязательно создайте новый резервный комплект.

Кнопка «Создать новые резервные коды» доступна в настройках владельцу текущего сеанса и **заменяет все ранее выпущенные коды**. Коды показываются только после выпуска.

## Когда оба способа недоступны

Для аккаунта, у которого нет ни действующего сеанса, ни заранее выданного кода, невозможно безопасно восстановить доступ по одному публичному имени пользователя. Нужна ручная проверка владельца администратором. Для прежних владельцев с доступом к своей инфраструктуре это может быть подтверждение права управления Cloudflare и адресное изменение `password_hash` администратором. Не следует размещать незащищённый публичный API для сброса пароля или публиковать новый пароль в чате/issue.

Восстановление по email не реализовано: существующие аккаунты не содержат предварительно подтверждённого адреса. Простое поле «email» без предварительного доказательства владения не является безопасным способом возврата аккаунта.

## Детали безопасности

- Пароли продолжают хешироваться в том же формате PBKDF2-SHA256; оригинал пароля не хранится.
- HTTP cookie имеет `HttpOnly; Secure; SameSite=Lax`, максимум 30 дней. Обычный срок сеанса не бесконечен.
- Для кода используется криптостойкий генератор, формат проверяется до хеширования, код приводится к верхнему регистру.
- В API смены пароля с доверенного устройства достаточно существующей сессии. Следует учитывать, что украденная cookie позволяет эту операцию. В будущем добавить повторную проверку при особо важных изменениях и дополнительные факторы.
- Высокоэнтропийные коды защищают от перебора, но для публичного сервиса всё равно желательно добавить ограничение частоты запросов, аудит входов и уведомление об изменении пароля.
- На регистрации, после сброса и при перевыпуске показывайте коды только один раз; не храните их в локальном хранилище браузера или журналах.

## Автоматические проверки

`test/account-recovery.test.js` проверяет регистрацию, получение только хешей, одноразовость, неверный код, отзыв старых сеансов, восстановление владельца без смены userId, смену пароля с действующего устройства и недопущение анонимной смены.
`test/auth-recovery-interface.test.js` проверяет отдельные формы и доступность элементов управления.
